# Direct-Mapped Cache Controller — Final Technical Report

Verified locally on 16 November 2026. Team integration base: Git commit `ba8d39d`. Local corrections and supporting artifacts are uncommitted for review. No remote changes were made.

## Objective and scope

Implement a synthesizable, read-only direct-mapped cache and measure its behavior under sequential, random, repeated and conflicting accesses. The subsystem is blocking and supports one outstanding aligned 32-bit load. A backing memory returns four 32-bit words per missed 16-byte block. This implementation does not include CPU stores, byte-load formatting, unaligned loads, coherence, or a physical board wrapper.

## Architecture and operation

Cache capacity is 1 KB: 64 lines, each holding 16 bytes. A 32-bit byte address contains a 22-bit tag, 6-bit index, 2-bit word offset and 2-bit byte offset. Total array storage is 9,664 bits, including tags and valid bits. See [architecture diagrams and state transitions](../docs/architecture.md) for the system diagram, controller FSM and refill FSM.

The top-level hierarchy is:

```text
cache_top
├── cache_controller
│   ├── address_decoder
│   ├── tag_comparator
│   ├── cache_data_ram
│   ├── tag_ram
│   └── valid_bit_ram
└── main_memory_interface
```

The testbench attaches `main_memory_model` outside the synthesizable hierarchy. Reads of cache arrays are combinational; writes are synchronous. Reset clears valid bits and aborts any pending transaction. A hit requires both a valid entry and tag equality. On a miss, the controller holds the accepted address, requests the aligned block, waits for four words, and writes data/tag/valid before responding. Data word 0 occupies refill bits [31:0].

## Functional verification and waveforms

All five dedicated testbenches pass with Icarus Verilog. The integrated testbench checks returned data, independent reference hit/miss expectations, aligned memory addresses, exactly four memory word reads per completed miss, no memory traffic on hits, one response per accepted request, stall behavior, and reset during a pending refill. Module-level tests additionally cover storage isolation, write enables, every tag comparison bit, boundary addresses, immediate and delayed memory responses, and controller behavior.

System traces execute 5,040 requests over twelve cold-cache runs (four traces × word-memory latencies 0, 1 and 5). Including directed tests: 5,043 accepted requests, 5,042 responses and one request deliberately aborted by reset. Assertions establish this accounting relationship. All committed trace files reproduce byte-for-byte from the deterministic generator.

Evidence: [full simulation log](simulation.log), [actual VCD waveform preview](waveform.svg). The full generated 18 MB waveform is `build/tb_cache_top.vcd`; it is intentionally excluded from Git and regenerated by `make waveforms`. The SVG shows the first 1,200 ns of actual transitions, including initial reset/aborted transaction/recovery. Data and protocol correctness are checked by testbench assertions across the full run; the preview alone is not the verification oracle.

## Performance and architectural analysis

Hit response latency is 2 cycles. The measured miss response latency is `9 + 4L` cycles, where L is the configured word-memory latency. Thus the additional miss penalty is `7 + 4L` cycles:

`AMAT = hit_time + miss_ratio × additional_miss_penalty`

At L=5:

| Trace | Requests | Hits | Misses | Hit rate | AMAT (cycles) | Simulated AMAT (ns) |
|---|---:|---:|---:|---:|---:|---:|
| Sequential | 512 | 384 | 128 | 75.00% | 8.7500 | 87.50 |
| Random | 512 | 112 | 400 | 21.875% | 23.09375 | 230.9375 |
| Repeated | 512 | 480 | 32 | 93.75% | 3.6875 | 36.875 |
| Conflict | 144 | 32 | 112 | 22.222% | 23.0000 | 230.00 |

The nanosecond values assume the testbench's 10 ns period, not a demonstrated 100 MHz hardware clock. At a conservative 80 MHz benchmark operating point, multiply cycles by 12.5 ns instead. AMAT measures acceptance-to-response latency, while elapsed trace cycles also include issue intervals.

Sequential accesses exploit spatial locality: one miss fills four adjacent words. Repeated accesses exploit temporal locality after warm-up. Conflicting blocks evict each other even when total useful data could fit in a more associative cache. Random accesses expose weak locality and working-set effects. Full twelve-run measured results, independently checked against a Python cache model, are in [performance.md](performance.md) and [performance.csv](performance.csv).

## Comparison against alternatives

Compare the direct-mapped design against equal-capacity 2-way and fully associative LRU reference models, each with 64 blocks of 16 bytes and a cold start. For the conflict trace, hit rates improve from 22.22% to 63.89% and 95.14%, respectively. For random accesses the corresponding rates are 21.88%, 23.05% and 25.78%. Sequential and repeated hit rates remain unchanged. These are trace-model alternatives, not synthesized alternative RTL. Additional comparator/replacement cost and timing are not measured, so no hardware speed-up is inferred.

Relative to uncached traffic of one word per request, this cache fetches four words per miss. The sequential trace reads 512 words, repeated reads 128 words, random reads 1,600 words and conflict reads 448 words. Block refill can therefore increase traffic when locality is poor. A no-cache CPU latency comparison would require an explicit adapter and is not claimed.

## Synthesis and routed timing

Tools: OSS CAD Suite release 2026-11-16, Yosys 0.71+39 (`40ab7d308`), nextpnr-ecp5 0.11.1-92 (`5e2718b6`), Icarus Verilog 14.0 development build bundled with the suite. The complete suite lives in ignored `work/tools/`; it is not part of the source submission.

Yosys reports that the resettable valid-bit array is lowered to registers, which is expected for its global asynchronous clear. ABC also emits combinational-network notices during mapping; structural checks complete without errors.

Three synthesis flows exclude the behavioral memory model and pass structural `check -assert`:

| Flow | Measured resources / result |
|---|---|
| Technology-independent | 20,841 cells, including 9,600 unreset enabled data/tag flip-flops after memory lowering; longest combinational topological path 21 cells |
| Xilinx 7-series mapped synthesis | 420 flip-flops (419 FDCE + 1 FDPE), 297 LUT2–LUT6 cells, 150 RAM64X1S distributed RAM primitives, 1 BUFG, 68 input and 67 output buffers |
| ECP5 mapped synthesis | 1,012 LUT4, 420 TRELLIS_FF, 152 TRELLIS_DPR16X4, 211 PFUMX, 70 L6MUX21; counts are before packing |
| ECP5 post-pack utilisation | 1,924/24,288 TRELLIS_COMB (7.92%), 420/24,288 flip-flops (1.73%), 152/3,036 RAMW (5.01%), 0/56 block RAMs, 135/197 I/O sites |

Asynchronous cache reads map to distributed memory, not synchronous block RAM. The generic flip-flop count is not the FPGA-mapped flip-flop count. Primitive and packed-resource counts describe different stages and must not be added together.

Device benchmark: LFE5U-25F, CABGA256, speed grade 6, seed 1. Post-route estimated internal register-to-register Fmax is **94.84 MHz**, approximately **10.54 ns** critical-path period. The **100 MHz target fails**; a separate **80 MHz target passes** at final routing. Early pre-route timing estimates in the logs are not the final result. The conservative benchmark operating point is 80 MHz (12.5 ns period).

The critical routed path traverses tag lookup/control and the CPU data-register enable. The top has automatically placed, unconstrained I/O; no real board pinout, external input/output timing budgets, reset recovery constraints or backing-memory device timing was supplied. Therefore 94.84 MHz is a tool-estimated internal timing result for this device/seed, not a board-qualified system guarantee. Xilinx synthesis has no routed frequency result. Preserve both the failed 100 MHz experiment and successful 80 MHz report.

Raw evidence is in [synthesis/](synthesis/): mapped/generic statistics, logic depth, complete routed timing logs and JSON timing reports. `--timing-allow-fail` is absent from the final Makefile, so a failed timing target makes the benchmark command fail.

## Reproduction and next steps

Follow [docs/demo.md](../docs/demo.md). Activate the local tool path, run all tests, regenerate the waveform and analysis, then run generic/Xilinx synthesis and ECP5 synthesis/routing. The downloaded toolchain and build outputs are ignored; evidence summaries/logs are retained in reports/.

For a board implementation, choose the actual FPGA board, provide clock/reset and pin/I/O constraints, connect a real memory or on-chip backing-memory wrapper and a stimulus/display interface, implement with the relevant vendor flow, and validate on hardware. A synchronous RAM/pipelined lookup variant could improve FPGA memory efficiency and timing but changes hit latency and requires a new verification/performance comparison.
